# Capture data contract

This is the contract used by the capture skill. Do not invent fields outside these shapes.

## Files

| Path                      | Purpose                                              | Ownership                                          |
| ------------------------- | ---------------------------------------------------- | -------------------------------------------------- |
| `_staging/walk.json`      | raw nodes, edges, decisions, and staging asset paths | authored during exploration                        |
| `<date>/graph.json`       | observed graph plus screen-identity corrections      | assembled source; only `overrides` is edited later |
| `<date>/flows.json`       | reader-facing semantic flow package                  | authored semantic source                           |
| `<date>/view.json`        | canonical screens, semantic flows, replay, coverage  | generated and committed                            |
| `app.json`                | app metadata and capture index                       | authored manifest                                  |
| `assets/<hash>.png`       | content-addressed screenshots                        | generated by assembly                              |
| `assets/<hash>.snap.json` | local accessibility snapshots                        | generated, gitignored, not deployed                |

## `walk.json`

```ts
interface Walk {
  meta: Omit<GraphMeta, "schemaVersion">
  root: string
  mainNav?: string[]
  nodes: {
    id: string
    role: ScreenRole
    shot: string | null
    snap?: string | null
    texts?: string[]
    interactiveElements?: InteractiveElement[]
  }[]
  edges?: {
    from: string
    to: string
    action: string
    selector?: string | null
    kind?: "nav" | "overlay" | "in-place" | "back"
    observedAtStep?: number
  }[]
  decisionPoints?: DecisionPoint[]
  overrides?: Overrides
}
```

The walk records observation only. Assembly computes `fingerprint`, `skeletonHash`, `pHash`,
content-addressed asset paths, and ordinary `nav` versus `in-place` edge kinds.

## `graph.json`

```ts
interface Graph {
  meta: {
    schemaVersion: 2
    app: {
      name: string
      slug: string
      bundleId: string
      platform: "ios" | "android"
    }
    captureDate: string
    scope: "initial" | "full" | "flow"
    mode: "guided" | "free-roam" | "replay"
    previousCapture: string | null
    durationSeconds?: number
  }
  root: string
  mainNav?: string[]
  nodes: GraphNode[]
  edges: GraphEdge[]
  decisionPoints: DecisionPoint[]
  overrides: Overrides
}
```

`GraphNode` adds these assembled fields to the raw observation:

- `fingerprint`: `sha256:` or `sha256-text:` exact identity;
- `skeletonHash`: structure-only identity;
- `pHash`: perceptual screenshot hash or `null`;
- `screenshotPath`: content-addressed PNG path; and
- `snapshotPath`: content-addressed local snapshot path or `null`.

`GraphEdge` contains `from`, `to`, human-readable `action`, replay `selector | null`, `kind`,
and `observedAtStep`. Every referenced root, nav item, edge endpoint, decision node/target, and
override node must exist.

### Graph overrides

Graph overrides correct observed screen facts only:

```ts
interface Overrides {
  screens?: Record<
    string,
    {
      role?: ScreenRole
      title?: string
      description?: string
      state?: string
      stateGroup?: string
    }
  >
  merges?: string[][]
  splits?: string[]
}
```

- `screens` corrects role/presentation or forces screen derivation membership and labels.
- `merges` forces observations to one exact canonical screen.
- `splits` keeps observations distinct when structural signals are too coarse.

`flowNames` and `structure` are retired and rejected. Semantic changes belong in `flows.json`.

## `flows.json`

```ts
interface FlowsFile {
  schemaVersion: 1
  flows: {
    id: string
    name: string
    summary?: string
    parentId: string | null
    order: number
    steps: string[]
    entryPoints?: {
      flowId: string
      fromScreenId: string
      toScreenId: string
    }[]
  }[]
  uncovered: Record<string, string>
  flowTODO: { about: string; question: string }[]
}
```

- `id` is a unique human-readable kebab-case semantic id and the public URL slug.
- `parentId` is the canonical semantic placement; top-level flows use `null`.
- `order` controls sibling order, with id as the deterministic tie-break.
- `steps` contains ordered local presentation screens. Every flow has at least one, and every
  entry renders. References may be raw ids; deterministic canonicalizations are reported.
- `entryPoints` records the other flow and exact source/destination screens that visibly expose
  this intent. Screen references may name a concrete derivation of a local step. It does not
  create tree nodes or affect replay.
- `uncovered` explains intentional omission of a canonical screen or derivation group.
- `flowTODO` records unresolved authoring questions and is empty in committed captures.

Author one concrete member of a derivation group in a flow. Other group members share its
coverage and generated occurrence. See [flow-grouping.md](flow-grouping.md) and
[naming.md](naming.md).

## `view.json`

`view.json` is generated by `packageGraph(graph, flows)` and not edited. It contains canonical
screens and derivation metadata; ordered semantic flows with optional context tiles; entry
points; replay status/commands; unique decision links; reverse `appearsIn` occurrences;
coverage/disposition stats; and non-blocking diagnostics.

A context `ViewStep` may include `variationIds: string[]`. These are the concrete members of the
step's derivation group with a recorded transition into the child flow. Authored steps omit the
field and retain the full derivation switcher; exact entry-point capabilities are likewise shown
only on the concrete source/destination screen named in `flows.json`.

## Validation

`assemble.ts` validates observed graph structure. `flows.ts validate` runs semantic validation
in draft mode unless `--strict` is supplied. `package.ts` and `build-data` are strict: every
source must be present and valid, every flow must have a local step, parent/entry references
must resolve without cycles, every logical screen must be covered or uncovered, and `flowTODO`
must be empty. A single-child parent emits a non-blocking hierarchy advisory.

The same command also runs separate naming validation: canonical screen and flow names use
spaced words, and variation labels are non-empty and remain unique after lowercase URL
normalization. Naming findings never determine semantic membership or hierarchy.

Replay transitions and selectors are diagnostic rather than semantic validation errors.
